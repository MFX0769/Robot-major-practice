# /pre-compact — Pre-Compact 审计

## 用法

```bash
/pre-compact             # 完整执行审计流程
/pre-compact --check     # 仅检查不写入
```

## 流程

### 1. 扫描会话

从当前会话提取所有未记录的：
- 技术决策
- Bug + 根因
- 实验结论
- 用户决策
- SOP/Skill 变更

### 2. 对照 daily_review.md

逐条对比补缺，追加到文件尾部。

### 3. 检查 git workspace

```bash
git status
git diff --stat
```

判断是否需提交：
- 日志/文档 → 提交
- 发货产物 → 提交
- 临时测试文件 → 不提交
- 代码变更 → 仅当任务相关时提交

### 4. 按模块归档日志

不同模块的日志分别记录到不同工程的日志：
- 遥控器（rc_remote）→ `develop_log/daily_review.md`
- Linux_ws（H3/板卡/压测平台）→ `linux_daily.md`
- 透传（kmo_mc_rcv）→ 该工程自己的日志
- 跨会话交接 → `develop_log/handoffs/`

确认当前会话涉及的模块日志已补齐。

### 5. 写清后续计划（强制 · 2026-09-26 用户增补）

压缩前必须在 handoff（或 daily 尾部）写**完整的排序计划**，只有"下一步"一句话不算过：
- **主线刀序**：每刀一行——做什么/改哪/预期/依赖/判据（可 A/B 的量化判据，不是"看看效果"）
- **支线**：并行项与各自等待条件（等谁拍板/等什么数据）
- **运维线**：自转中的任务（闹钟/监视/扫描）与"勿动"标注
- 执行纪律一句话（如"每刀 A/B 落盘再切下一刀；负结果同样落盘"）

### 6. 确认通过

五项（会话补齐/git/归档/后续计划/**跨会话环境对账**，见 §10）全通过后再压缩。

> 详细 SOP: `develop_log/sop/pre_compact_audit.md`

### 7. 压缩后交接强化（2026-09-27 增补 · 社区调研 post-compaction amnesia 对症）

- **handoff 头部强制写「压缩后第一动作」**：新会话先读什么、向用户复述什么、等谁拍板——不写视为未完成（今天 09-27 的教训：内容全但没写执行指示，新会话读了也漂移）。
- **计划指针有效性检查**：handoff 引用的计划文件路径必须核实存在且为最新版（同主题多版本时以日期最新为准，旧版标 superseded）。
- **观测器/串口状态清点**：收尾时必须写明观测器进程与 COM 占用（哪些在跑、谁持有哪个口）。
- **会话扫描清单加一项**：本会话新增的 fw 打印/探针，是否已同步采集工具的 keep 列表（09-27 三次过滤器吃行教训）。

### 9. 注入提示词模板（v4 · 2026-11-09 增补 · 项目版为准）

> v4 两处关键改进（11-09 用户点出）：
> 1. **问法从「是否知道要做什么」改为「第一件事 + 明确不做什么」**——前者只能换来复述，后者能逼新会话去读 Dead Ends。
> 2. **加读取优先级**——计划/日志/handoff 冲突时先信谁，必须写死，否则新会话会拿旧计划里的过期结论当现状（11-09 实例：旧闹钟把已推翻的 `peer=255` 当"唯一卡点"）。

```text
【接续注入 · <日期>】
下一会话主题：<用户原话；缺失则本提示词无效>

一、先按序读（≤5 份），冲突时按此优先级裁决：
  1. <最新 handoff>            ← 最高优先级，冲突以它为准
  2. <计划正本> 的「当前状态/进度快照」节  ← 次之
  3. <实验日志> 当日关键时段（含自我更正条目） ← 再次
  4. <专题改动清单/设计文档 1-2 份>
  > 2 与 3 矛盾时以 2 为准；3 里"更正"条目优先于同段旧结论。

二、开场行为协议（违反即返工）：
  1. 复述，不展开：≤10 行人话——计划是什么、为什么、第一阶段是什么；缩写首次出现必须展开。
  2. 回答两问（不是"是否知道"）：
     a) 你要做的第一件事是什么？用两行说清「你做什么 / 我做什么」。
     b) 哪些事你明确不做？列出你看到但决定不碰的（逼读 Dead Ends）。
  3. 用户确认前禁止：写代码、烧录、抓串口、派子代理、输出细化长文。只允许读、复述、提问。
  4. 确认后引领第一步，等用户说开始。

三、最小状态事实（≤5 行，只写"是什么"不写"为什么"；含环境差=§10 对账结果，无变更写"已查 X 仓无"）。

四、Dead Ends（≤3 条）：本会话明确否掉/证伪的路径，防重复踩。

五、没测清单（≤3 条）：交接里未验证的断言。

六、纪律：常驻禁令见 AGENTS.md，本注入只指向不重复。
```

**红线**：
- 注入词 ≤30 行；超了删细节、留指针。
- 禁止把"当前状态数字"写成不可变事实——只写"读哪份文件"，状态以文件为准。
- 第 2 步的 (a)(b) 两问不可合并成"是否知道要做什么"。

### 10. 跨会话环境对账（2026-11-20 增补 · 硬门禁）

压缩前必读关联仓（本仓 rc_remote / 透传 kmo_mc_rcv / 踏频主树 / GD 仓，按主题选）daily 自上次 handoff 以来的尾部，提取**会推翻本会话环境假设的变更**：RF 地址族/信道/配对槽、他板固件版本、接线/探针/端口、供电态。

- 有变更 → 写进 handoff「环境假设清单」（下一会话计划依赖的环境前提，每条带证据或标"未验"）+ 注入词最小状态事实。
- **查无变更也要写"已查 X 仓 daily 尾部，无环境变更"**（覆盖证明，禁静默）。
- 教训（2026-11-20）：本仓会话 11:45 改桥+遥控族 C5（记本仓 daily 11:45/11:47），踏频板留旧 CC 址未跟上→无线断；踏频仓压缩门禁全 PASS 但无人读本仓 daily，下一会话子代理盲跑 20 分钟。**改地址方有义务在消费方仓 daily 留一行索引**（devlog-append §7 环境变更跨仓通报）。
