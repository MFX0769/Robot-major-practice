# overnight-alarm — 彻夜自主迭代闹钟

**一句话**：闹钟不是定时器，是**给未来那个没有上下文的自己的一份自指令**——写错了会空转刷屏一整天。

## 何时用

- 用户要“彻夜/整夜/每 N 分钟自主迭代”
- 计划换了正本，旧闹钟还指着旧文件
- 闹钟把额度跑没了 / 同一条提醒重复触发很多次

## 硬规则（每条都有事故背景）

1. **先 `CronList` 再动手**——今天的事故：旧闹钟没删，两个并存，同一轮提示连发 20 次、`runCount=83`。
2. **闹钟 prompt 里不写“当前状态数字”**，只写“开轮先读哪份文件”。
   - 原因：状态每 30 分钟就变，写死=24 小时内必然过期（今天就有 `bm=2`/`peer=255` 这类过期描述）。
3. **必须带停止条件**：连续 2 个检查点无进展 → 写 handoff 并 `CronPauseSelf`，不许空转。
4. **必须带端口硬边界与禁 push**：闹钟是无人值守，越权没人拦。
5. `CronCreate` **没有 model 参数**——它用当前会话的模型。额度不足的模型上挂闹钟=每 30 分钟空跑一次。换套餐=删掉重建（CronUpdate 改不了模型）。
6. 标题保留用户的自然语言周期（如“每30分钟”），改周期必须同步改标题。
7. 每次改完用 `CronList` 复核：`title / cronExpr / enabled / runCount` 四项。
8. **★反偏见条款（2026-11-10 用户令）**：偏见一旦生成，agent 会对闹钟**置若罔闻**——闹钟照常触发，agent 继续干自己惯性里的事（追根因/修台架），把闹钟里的优先级当参考。对策：
   - 闹钟 prompt 必须**内嵌用户的目标清单原文（P1→P10 逐条）**，不能只给文件指针——指针会被惯性跳过，清单不会。
   - 开轮第一问固定为：**「过去 2 小时产出了清单里的哪几个数字？」**——答不出具体数字=立即切到清单首项，不许先"补一个根因"。
   - 目标清单必须**由用户提供或经用户确认**；agent 不得自行替换、缩减、重排序（防偏见写进源头）。
   - prompt 里与优先级同地位写明「禁止事项」（如：禁止追打印的源码根因；禁止全擦/换包除非判据预注册）。
   - 每轮产出物必须是**数字或 commit**，两者皆无=该轮计空转（计入停止条件）。
9. **★措辞必须强鞭策（2026-11-10 用户令）**：闹钟 prompt 是写给"正在偷懒/跑偏的自己"的，措辞要像监工不像备忘录：
   - 用**第二人称命令式+事实对峙**开头，例如：「你昨晚 8 次闹钟全在偏题、零数字产出——现在回答：过去 2 小时产出了清单里的哪几个数字？」
   - 把用户原话的批评引用进 prompt（如「用户令：目标是压测数字，不是修问题」），让每一轮都直面它。
   - 禁止软化措辞（"可以考虑""建议"），全部换成「做 X / 禁止 Y / 答不出=切首项」。
   - prompt 里写明**本夜不完成的后果**：明早收口报告将逐项列出「欠账+原因」，原因里不许出现"设备死了"除非有 10s+RTS 唤醒后的证据。

## 标准流程

```
1. CronList                      # 看有没有旧闹钟（重复的直接 CronDelete）
2. 读计划正本与最新 handoff        # 确认唯一执行正本路径
3. CronCreate(intervalUnit=minute, interval=N, recurring=true)
4. CronList 复核四项
5. 回复用户：一句话周期 + 第一个动作
```

## prompt 模板 v3 · 监工版（2026-11-10 夜实战验证有效，照抄改清单即可）

> **为什么不是 v1**：v1 只给文件指针（"读计划 §18"），8 次触发全在追根因、零压测数字——指针会被惯性跳过。v3 把目标清单**原文内嵌**、开轮第一问改成质问"交出数字"，才压住偏题。
> 实测：v3 一夜产出配对 767/790=97.1%、F 臂三臂、F4 84/100、J0 PASS；v1 前 3 小时零压测数字。

```
【监工 · <日期> <起> → <止>】你昨晚 <N> 次闹钟全在偏题、零数字产出；用户令原话：「<引用原话1>」「<原话2>」。
现在回答第一问，不许多想：**过去 2 小时产出了下面清单里的哪几个数字？** 答不出具体数字 = 立即切清单最前面的未完成项。
不许追根因、不许修台架、不许造轮子（已有脚本不重写）。本轮产出必须是数字或 commit，否则这轮=空转（连续 2 轮空转=停机）。

【<战役一名称>】
<循环体逐步骤写；产物路径；每轮记什么数字；失败分类枚举>

【<战役二名称>】
<照设计文档 §X 做；落点=文件:函数；判据逐条编号；验臂顺序>

【<战役三名称>】
<...>

【机器判据】<端口在场/服务存活/日志在长>；<设备静默的正确判据：先读 10s+RTS 唤醒，禁直接判死；设计态打印先查文档>
【端口硬边界】<列出授权端口>；其余禁碰。
【红线】禁 push；<项目专属：烧录前台见 Writing Flash OK / 0xCF 写后读回 / 禁主动 0xA5 / 禁手写 0xAC slot1 / 手机只走 unlock.sh ...>
【停止条件】连续 2 检查点无新数字/新提交 → 写 handoff + CronPauseSelf；到 <终止时刻> 也 CronPauseSelf 并写收口 handoff（欠账项原因里不许出现"设备死了"除非有唤醒后证据）。
```

**填写要点（缺一条 ~v1）**：
1. **清单必须是数字指标**，不是任务描述（"配对 N=10 出成功率" ✅ / "做配对压测" ❌）——换主题必重写，否则偏题换形式回来。
2. **引用用户原话**（批评/命令，不带引号就失效）。
3. **第一问用质问句式**，且答不出有明确后果（切首项）。
4. **红线与优先级同地位**（同一层，不是附录）。
5. **停止条件写具体时刻**，并预注册"欠账原因不许是 X"（防假病）。
6. 模板 ≤30 行；超了删细节留指针（清单本身不许删）。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| prompt 里写满当前数字 | 半天后全是过期事实，下一个会话被误导 | 只写“读哪份文件” |
| 不删旧闹钟就新建 | 双重触发、刷屏、额度耗尽 | 先 CronList → CronDelete |
| 在没额度的模型上建 | 每轮空跑、runCount 暴涨 | 确认会话模型额度 |
| 只写“继续迭代” | 醒了不知道干什么，容易重复劳动 | 写清“只做什么/不做什么” |
| 不写停止条件 | 无进展也一直跑 | 2 检查点止损 |
| **prompt 只给文件指针，目标藏在文档里** | **agent 被惯性带走，对闹钟置若罔闻（11-10 夜实测：8 次触发全在追根因）** | **目标清单 P1→P10 原文内嵌 + 开轮第一问“上 2h 产出了哪几个数字”** |
| **agent 自行替换/缩减目标清单** | 偏见从源头写入，用户醒来发现做的不是要的 | 清单由用户提供或确认；改清单=用户拍板 |
| **清单写成任务描述（"做配对压测"）** | 可无限"深化"、永远不算完成，偏题换形式回来 | 写成数字指标（"配对 N=10 出成功率"） |
| **多批并发/旧批复活** | 11-10 04:15 实测：kill 只杀父进程→旧批复活与新批抢同一部手机→62% 假失败 | 后台批 kill 必须进程树；启新批前校验无残留进程 |
| **台架态前提没写进 prompt** | 混合态下测 J0 得 p0=2.95 判 FAIL（门前提是巡航纯 2.4G） | 每条判据旁写"该判据成立的前提态" |

## 收口检查单（到终止时刻必做）

1. 机器判据最后跑一次（端口/服务/日志在长），结果入 daily
2. 三战役逐项写：**数字 / 口径 / 失败分类 / 终态（✅🟡❌⏸）**
3. 未完成项必须写**原因 + 解锁条件**（原因禁用"设备死了"除非有 10s+RTT 唤醒证据）
4. handoff 加「早晨第一动作」（一条命令级）
5. RAM 态清单（断电/重烧即失的项）单独列
6. `CronPauseSelf` 停机 → `CronList` 确认 enabled=false

## 停用/删除

- `CronDelete(id)`：彻底删，历史一并清
- 只想临时停：把 cron 推到久远日期（如 `0 0 29 2 *`）或 `enabled=false`（若工具支持）
- 删除后 `CronList` 确认列表干净


> **2026-11-20 补充**：写停止条件时禁用"必须人来操作"类出口，除非已穷尽**台架自主运维四能**（UART 字节唤醒深睡/复位引脚通道 124=pw-rst 专用时序/adb input 解锁手机/杀白名单口占用进程）——正本=统筹SOP §八 + AGENTS.md 规则 26。真边界只剩硬件物理故障与授权决策两类。
