## SBUS真正的根因：DMA缓冲区长度配置错误（纯软件bug）
顺着"波特率/DMA是否配好"这个思路查代码（用户提问"115200？串口dma都注册号了？"带出来的），发现`Comm/usart_comm.h`里：
```c
#define DMA_DBUS_LEN  18
```
USART1波特率/校验/数据位配置本身是对的（100000, 9bit=8data+偶校验，符合SBUS协议要求），不是这个问题。
但SBUS一帧是25字节(`SBUS_FRAME_SIZE`)，DMA缓冲区只给了18字节。链路：DMA配置成只收18字节（非循环模式，收满就停），每帧后7个字节根本没被接住；IDLE中断触发后调用`sbus_callback_handler(dma_dbus_buf, DMA_DBUS_LEN)`传长度18，函数第一行`if (len < SBUS_FRAME_SIZE) return;`即`18<25`恒真，**每次调用直接返回，从未真正解析过一帧**。这就是`wbus_rx_cnt`和所有通道值永远为0的真正原因，跟BTB连接器、波特率都无关。

**修复**：没有改名`DMA_DBUS_LEN`/`dma_dbus_buf`（避免和D:\侧命名冲突——D:\的`DMA_DBUS_LEN=18`对应的是真正DBUS协议，rc_callback_handler，跟这边语义不同，不能混用同一个名字）。改为新增一组独立常量/缓冲区：
- `DMA_DBUS_LEN=18`（保留，给真DBUS协议用，跟D:\一致）
- 新增`DMA_SBUS_LEN=36`、`dma_sbus_buf[DMA_SBUS_LEN]`（SBUS实际用这个，36留余量，IDLE中断会提前abort，不需要精确等于25）
- 新增宏`SBUS_HUART`（=huart1，跟`DBUS_HUART`同一个物理口的另一个别名），`USER_UART_Init()`里SBUS初始化改用`SBUS_HUART`/`dma_sbus_buf`/`DMA_SBUS_LEN`，不再用DBUS命名的那一套
- 涉及文件：`Comm/usart_comm.h`、`Comm/usart_comm.c`

修复后烧录验证：`wbus_rx_cnt`从1240涨到1743（5秒+503，约100Hz，符合SBUS正常帧率），CAN1（imucnt/chassis_2006[0].receive_cnt）同步健康无回归。ch1/ch2/ch3读到0是因为遥控摇杆当时在中位（解码用`-1024`居中，中位摇杆算出来正好是0），不是bug。

## dbg_print打印摇杆/lock_flag/模式 + 给SBUS补上解锁手势
切回`DEBUG_TEXT_ENABLE=1`/`DEBUG_VOFA_ENABLE=0`，`chassis_task.c`原有周期打印(每500周期一次)扩展成：
```
[CHASSIS] mode=%d lock=%d sw1=%d ch1=%d ch2=%d ch3=%d ch4=%d rx[3]=%d rpm=%d
```

用户问"现在扣一下摇杆，就有lock_flag=1的吗？"——查证：`unlock_init()`(DR16)/`vtm_unlock_init()`(VTM)里确实有"摇杆四通道打对角极限组合才解锁"的逻辑，但我之前加的SBUS分支(`if(wbus_rx_cnt>0){直接用sw1映射ctrl_mode}`)完全绕开了这两个函数，根本不会调用，所以SBUS路径下lock_flag会一直停在初始值0，不会被任何操作置1。

用户要求"模仿他们的，给SBUS加上"——在`mode_switch_task.c`新增`sbus_unlock_init()`，直接照抄`unlock_init()`的判断逻辑(拨杆sw1中位 + ch1~ch4打对角极限组合，`ch4<=-600&&ch3>=600&&ch1<=-600&&ch2<=-600`解锁为1，反向组合解锁为2)，并把SBUS分支改成：
```c
if (wbus_rx_cnt > 0)
{
    if (!lock_flag) sbus_unlock_init();
    else switch(wbus_rc.data.sw1) { ... 原映射 ... }
}
```

## 关键现象：拨一下减速前的电机转子就能动，几乎必现
用户报告：右前轮卡住不动的时候，**用手拨一下减速器之前的电机转子(电机自己的轴，不是经过减速箱之后的轮子轴)，就能让它动起来**——这个规律几乎每次都成立。

这是典型的"卡死点"症状，跟之前手转轮子轴感觉到的"减速器阻力"是两个不同层面的现象(轮子轴那是经过减速比放大后的大力矩判断，这次是直接拨电机自己的转子，力矩小得多)。两个最可能的原因：
1. **三相动力线某一相接触不良/断开**：电调只剩2相通电时，磁场不再是平滑旋转的，只能在固定方向上产生力矩，转子停在某些角度时合力矩接近0，拨一下让转子转出这个角度后，剩下的力矩能继续把它带起来——跟现象完全吻合
2. **电机自带的霍尔传感器/编码器读数异常**：电调做闭环换相需要知道转子准确位置，如果传感器线路有问题导致换相角度算错，也会在特定转子角度下输出力矩很弱甚至接近0，拨一下转子让真实位置跟电调认为的位置重新对上后就能正常起步

两种原因殊途同归，都指向**电机自身的接插件(动力线三相+编码器/霍尔信号线)**，不是电调、不是CAN、不是代码。下一步应该直接检查右前电机本身这两组线的接插件是否插紧/有无氧化损坏。

## PID代码逐项复查：未发现额外bug，MaxOutput=500解释了之前的tx上限
用户要求"PID不可以排除，严查PID相关"。逐项检查`Math/pid.c`的`pid_calc()`/`pid_param_init()`/`abs_limit()`：

## digital始终为0，跟黑白线/校准状态都无关，怀疑校准状态被使能命令的时序问题清空
为了避免GDB attach可能引发复位干扰瞬态读数(本晚反复验证过的已知问题)，改用串口dbg_print常规验证：在`chassis_task.c`已有的500周期打印块里加一行`[8IR] state=%d pos=%d digital=%d...`，编译(0 Error)烧录(90016字节)。

用户观察：模块板载8个指示灯本身会随黑白线位置变化(右2暗/左6亮)，证明探头硬件层面在正常工作。但串口打印出来的`digital`持续读出`00000000`，跟物理位置完全不对应。

排查`parse_value()`逐字节核对(`strstr`定位key+`k+=3`跳过"x1:"这3个字符落在数字上)，逻辑对单数字索引x1-x8没问题；且早前抓到的原始DMA字节里数字本来就是"x1:0,...,x8:0"，证实**解析忠实反映了模块实际发送的内容**，不是解析层的bug。

怀疑跟校准状态有关(手册：未校准的模块红灯会"不停闪烁"，校准设定的是黑白判定阈值，决定UART上报的digital值；不校准可能导致分类逻辑固定输出0)。用户按手册流程做了一次校准(长按KEY1进校准→黑线3秒→按KEY1→白线3秒→按KEY1)。

校准完成后用同一份固件(代码未改)重新测试：用户分别在"全白"和"全黑"两个时刻截取`[8IR]`日志对比，**两个时刻的`digital=00000000`完全一样，没有任何变化**——说明仅校准这一步没有解决问题。

新的怀疑：使能命令`prot_8irtraking_cmd_read(0,1)`只在STM32开机时(`chassis_task`启动)发一次。如果校准操作发生在STM32没有重新断电重启的情况下，使能命令是在校准之前发的——手册没说清楚"进入/退出校准模式"是否会把模块内部的"持续上报"状态重置掉，如果重置了，校准完成后没有人补发使能命令，模块可能停留在某种默认状态。

**计划**：把使能命令改成`$0,1,1#`(`prot_8irtraking_cmd_read(1,1)`，数字+模拟都开)，调试打印加上`analog[0..7]`，同时把`HAL_UART_Transmit()`的返回值打出来确认TX命令真的发送成功。
**预期结果**：模拟量是原始读数，不依赖校准逻辑——如果`analog[]`能随黑白线变化，说明收发链路本身没问题，问题在校准/数字分类这一层(可能是使能时序被校准过程清空，需要在校准后补发使能或者干脆上电重发)；如果`analog[]`也是死的不变，说明问题在更底层的收发链路上(没发出去/模块没收到/模块没回)，需要进一步排查接线或波特率。
