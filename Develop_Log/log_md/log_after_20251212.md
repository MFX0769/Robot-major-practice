**开发日志 - 2026年1月7日 晚上（云台RTOS队列改造）**

**主题**：CAN 通讯架构重构 - 解决“一个CAN最多挂4个设备”的历史诅咒

**起因：一个队里流传多年的“经验铁律”让我开始怀疑**  
今晚一切的起点其实来自于一个很久以前就觉得奇怪的现象：  
队里前辈们一直强调“一个CAN总线最多只挂4个设备，多了就会出各种问题”（丢帧、电机抖、反馈乱、甚至系统卡死）。  
大家默认这是硬件极限或总线特性，但我觉得太离谱了——CAN协议理论上支持几十上百节点，工业机器人/汽车上常见多设备，为什么RoboMaster就卡在4个？  
再回想F407时代，1kHz高频发送时电机经常疯抖，降频后PID又明显变软；高负载下中断堆积、FIFO溢出、丢帧，这些现象当时归结为“硬件弱”，但现在迁移到H7 + FreeRTOS后，这些问题依然隐隐作祟。  
我突然意识到：**很可能不是硬件问题，而是软件架构的锅**——中断处理过重（直接解包+业务逻辑）、发送同步阻塞、无队列缓冲、任务/中断抢占导致的恶性循环。

**核心疑惑 & 想解决的问题**  
1. **中断接收过重**：旧代码在HAL_FDCAN_RxFifoXCallback里直接GetRxMessage → 调用User_CANx_RxCpltCallback → switch ID → 解包更新motor结构体 → 整个ISR执行几十us，高频反馈下FIFO溢出、丢帧。  
2. **发送阻塞/同步**：发送任务高优先级 + while等邮箱空（或直接HAL_AddMessageToTxFifoQ），高负载下任务卡住，PID循环被饿死。  
3. **全局tx_message race**：多任务并发调用发送，ID/头配置被覆盖。  
4. **队里“4设备铁律”**：本质是软件缓冲/异步能力不足，一旦设备多、消息率高，系统就崩；不是总线极限，而是“同步处理 + 无队列”导致的瓶颈。

**重构目标**  
- 让通讯层真正“RTOS化”：中断最小化（只采集塞队列）、处理异步（任务解包/发送）、分层干净（BSP纯HAL、COMM队列+任务、PROT协议）。  
- 彻底打破“4设备诅咒”：通过队列缓冲 + 非阻塞 + 策略重试，让CAN挂更多设备、支持更高频而不崩。  
- 为实习面试准备故事：从“历史遗留同步阻塞”到“异步队列分层”，量化实时性提升（ISR时间降90%、丢帧率可控）。

**今晚实际改动过程 & 最终结果**  
1. **BSP 发送层**：彻底去掉while等待和vTaskDelay，改成纯非阻塞尝试（HAL_FDCAN_AddMessageToTxFifoQ一次调用，根据HAL_BUSY判断邮箱满）。  
   - 引入静态const default_tx_header，发送时局部拷贝 + 改ID，消灭全局tx_message race隐患。  
   - 删除无用的bsp_can_tx_init（默认配置移到const结构体）。  

2. **Tx任务层**：从队列取帧 → 调用BSP非阻塞发送 → 如果BSP_CAN_LINE_BUSY就vTaskDelay(1ms)重试 → 最多5次（≈5ms总等待） → 超限丢帧/统计。  
   - 等待策略完全上移到任务，可调宏（TX_RETRY_MAX/TX_RETRY_DELAY_MS），关键帧可延长，非关键可立刻丢。  

3. **结果**  
   - BSP层：零RTOS依赖、零阻塞、零状态，极致干净。  
   - 通讯整体：异步 + 队列缓冲 + 上层智能限速，负载高时自动丢非关键帧，系统不雪崩。  
   - 丢帧可控：5ms内瞬时满基本解决，超过说明总线真过载（可降频或分CAN）。  
   - 预计打破“4设备铁律”：队列缓冲后，挂6-8设备+高频反馈应该稳（后续实测）。  

**一句话心得**  
“CAN的极限不是硬件，而是软件有没有能力‘等得起、丢得起、缓冲得起’。  
队里4设备的铁律，其实是‘同步阻塞 + 无队列’的副产品。  
异步队列 + 非阻塞尝试 + 上层重试策略，才是真正能让机器人‘动起来’的底层之道。”
