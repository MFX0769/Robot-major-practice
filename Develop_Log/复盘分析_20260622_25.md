## 五、"为什么感觉做什么都没用"的真相（用你的数据）

你的感觉是对的：**确实每次修好一个就冒出一个**。这是工作流时序而非你的判断力问题：

```
修好 CAN id 冲突 → 暴露左后电调损坏（硬件）
修好左后电调 → 发现拨码错配（物理检查）
修好拨码 → 右后电调彻底烧了（新故障）
换好右后电调 → 右前轮仍然不动（这其实一直没解决）
修好右前 MaxOutput → 发现前后方向反了（新问题）
修好方向 → 8IR digital 全 0（又发现新问题）
修好 8IR GPIO → HardFault（两个改动的交叉影响）
修好 HardFault → 仍然 HardFault（第二次，更深的根因）
```

**连续 8 步"修好 A → 冒出 B"。换了任何人在这条链条上走到第 5 步都会产生"我做的一切都没用"的幻觉。** 这不是学习性无助，这是**现实性的"问题队列太长"**。

## 六、可复用的经验（如果下学期还有）

### 6.1 工具链检查清单（开工前 30 分钟做完）

- [ ] GDB attach 会不会触发复位 → 是的话放弃 GDB，只用串口日志
- [ ] Keil `-b` 能不能识别外部修改 → 不行就用 `-r` 全量编译
- [ ] OpenOCD 烧录后确认 `wrote xxx bytes`
- [ ] 确认当前有几个 AI 终端在工作，各自在改哪些文件

### 6.2 诊断流程：先查软件，再查硬件

遇到"不动"类问题时，查的顺序应该永远是：

```
1. 参数/配置（MaxOutput、Scale、宏开关）→ 2分钟
2. PID 计算路径（target→pid_out→tx_current）→ 10分钟
3. CAN 发送（send_cnt 在不在涨）→ 2分钟
4. CAN 接收（receive_cnt 在不在涨）→ 2分钟
5. 电调拨码/接线 → 物理检查
6. 电机本体/减速器/三相线
```

这次大部分时间浪费在 5→6 之间反复横跳，而根因在 1。

### 6.3 强制单 AI 策略

多个 AI 终端同时改代码，最优情况效率翻倍，最差情况（就是这次）产生交叉冲突，事后要花双倍时间排查。**下学期如果还有这种极限项目，限制自己在同一时间只跟一个 AI 终端交互。**

### 6.4 睡眠

40 小时睡 5 小时，有效的清醒时间大概只有前 24 小时。后面 16 小时的产出质量断崖式下降，但错误率指数上升。**这个账不值得。**
