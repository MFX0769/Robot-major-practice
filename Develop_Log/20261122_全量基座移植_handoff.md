**FIFO watermark 中断配置（答任务书 A2）**：有内部 FIFO，两个独立。Accel：`0x49` bit6=1 开 FIFO + `0x48` bit0 选模式 + `0x46/47` 写阈值（字节）+ `0x58` bit1 映射 INT1（或 bit5→INT2）+ `0x53` bit3=1 输出使能；Drdy 用 `0x58` bit2。Gyro：`0x3D` 写阈值（帧，写即清 FIFO）+ `0x1E=0x88` 开 watermark + `0x18` bit2（INT3）/bit5（INT4）映射 + `0x15` bit6=1 开 FIFO 中断；状态从 `0x0A` bit4 读。注意 watermark 中断在 `FIFO_DATA` 读期间被抑制，latch 需读状态且 fill level 降到阈值以下才清（§4.9.3.3）。

#### A2. "读到的是新采样"的 3 种判据

1. **状态寄存器位**：Accel 读 `ACC_STATUS` 0x03 bit7（读数据寄存器自动清，可先读状态再 burst 读数据）；Gyro 读 `GYRO_INT_STAT_1` 0x0A bit7（自动清 280–400µs，轮询窗口极短，只适合快速响应或配合中断）。
2. **EXTI 中断信号**：PE10/PE12 上升沿触发（`gpio.c` 已配 IT_RISING，但原厂无 callback）；中断置 `data_ready` 标志 → 任务中 burst 读取 → 清标志。这是 1 kHz 最稳的判据，且能避免重复读同一帧。
3. **时间戳/计数器**：Accel `SENSORTIME` 0x18-0x1A（39.0625µs/LSB）判断相邻两帧时间差；Gyro FIFO `FIFO_STATUS` 0x0E bit[6:0] 帧计数 + overrun bit7；无 FIFO 时可用 DWT 周期计数自建序号，并检查 `FIFO_STATUS` overrun 与 accel skip frame。

#### A3. 原厂驱动读取方式与不足

`BMI088driver.c` `BMI088_read()`（:287-321）：accel 用 `BMI088_accel_read_muli_reg` 宏（先拉 CS，发 reg|0x80，再发 1 dummy，然后逐字节读 6 B）；gyro 从 `GYRO_CHIP_ID` 0x00 起 burst 读 8 B 并校验首字节 0x0F（可简化为从 0x02 起读 6 B）；温度读 0x22-0x23 共 2 B（宏自带 dummy 字节）。底层 `BMI088_read_write_byte()`（`BMI088Middleware.c:144`）每字节调用一次 `HAL_SPI_TransmitReceive`，单次 `BMI088_read` ≈ 19 次 HAL 调用、SPI2 仅 3.75 MHz、无 DMA、无 DRDY 判据（`osDelay(1)` 盲轮询）。原厂配置 Accel=800 Hz（`BMI088driver.c:129`）但 Mahony 固定 `sampleFreq=1000`（`MahonyAHRS.c:23`），实际 998 fps 是发送/循环频率而非传感器 ODR——**"≥1000 Hz 稳定结算"目前未成立**。

#### A4. 优化清单（按优先级，寄存器/函数级）

- **[P0-1] ODR 对齐**：`BMI088driver.c:129` `BMI088_ACC_800_HZ`(0xB) → `BMI088_ACC_1600_HZ`(0xC)（或保持 800 但明确 800）；`:146` `BMI088_GYRO_1000_116_HZ`(0x82) 与 Mahony 1000 Hz 已匹配，若上 2000 Hz 必须同步改 `MahonyAHRS.c:23` 的 `sampleFreq=2000`，否则积分发散。推荐先保持 Gyro ODR=1000 Hz、Accel 提到 1600 Hz，满足"≥1000 Hz 结算"且不动滤波参数。
- **[P0-2] 三次 HAL 字节调用 → 三次 DMA burst**：改写 `BMI088Middleware.c:144` 提供 `HAL_SPI_TransmitReceive_DMA` 封装；gyro 读 `0x02|0x80` 7 B、accel 读 `0x12|0x80` 8 B（丢弃首字节）、温度读 `0x22|0x80` 4 B；在 `HAL_SPI_TxRxCpltCallback` 解析+置 ready。SPI2 prescaler 32→16（3.75→7.5 MHz，H7 prescaler 为 2^n，10 MHz 只能靠提高 SPI123 时钟或换 prescaler=16 近似）。CPU 占用可从 ~19 次 HAL 调用降到 3 次 DMA 启动。
- **[P0-3] DRDY 驱动读取**：在 `stm32h7xx_it.c` 补 `HAL_GPIO_EXTI_Callback` 处理 PE10/PE12，置标志并用 `osThreadNotify`/任务通知唤醒 INS 任务，替代 `osDelay(1)` 轮询；Gyro 中断 280–400µs 自动清，须在中断后立即读。

#### A5. 原厂温控 PID 能否直接复用（KP100/KI50/KD10/MAX500/DES_TEMP40、TIM3 CH4）

**不能原样复用，需 3 处改动**（`App/imu_task.c:8-12,73-79`，TIM3 CH4=PB1、Prescaler=24-1、Period=10000-1、PWM1，`Core/Src/tim.c:163-184`）：
1. **不是标准积分**：`out = KP*err + KI*(err+err_l+err_ll) + KD*(err-err_l)` 的"I"项是最近 3 次误差之和，非累积积分，无积分饱和但也不是 PID；移植时可保留（实测有效）或改标准位置式 `integral += err*dt` + 抗饱和。
2. **采样率错配**：温度每 **1.28 s** 才更新一次，而控制环 1 kHz（每 1ms 跑一次 PID），99.9% 的控制输出基于同一温度值 → 过冲/振荡。必须把温控降频到 **≤1 Hz**（例如计数 1000 次执行一次）或按温度变化加入速率限制。`cmjang/CtrBoard-H7_IMU_Altitude` 就是把温控放在 `count%10` 的 100 Hz 分支里（仍偏快，但比 1 kHz 好）。
3. **饱和与硬件保护**：`out` 被钳到 0..500，对应 CCR4=0..500 / ARR=10000 → 占空比 ≤5%；若加热片未接/24V 未就绪，温度永远到不了 40°C，`out` 长期饱和 500。必须加"N 秒温度未上升则关 PWM"的超时保护和上电默认 0 占空比（原厂 `HAL_TIM_PWM_Start` 前未清零 CCR4，硬件复位后为 0，安全）。
补充：`DES_TEMP=40°C` 与温度零点 23°C 匹配（0.125°C/LSB，115°C 跨度=920 LSB）；Mahony `sampleFreq=1000` 固定，若最终循环不是 1000 Hz 必须同步改。`cmjang` 的 1600/50/40 + 1000 次零漂平均 + "温度接近 40°C 持续 300 次才标定"流程值得抄（`AC5_Code/App/imu_temp_ctrl.c`）。

## 十八、寻线 U7 深度诊断（2026-11-22 21:20）：uart 中断未触发 + ORE 溢出，硬件环回/HDSEL 均无效

2. `RxState=32(BUSY_RX) Err=0` → RX IT 初始已挂载。
3. 运行数秒后出现 **`Err=8`（HAL_UART_ERROR_ORE，接收溢出）**：有字节进了 RDR，但 RXNE 中断没进回调 → `ir_isr_bytes` 始终 0。

## 二十、软件 I2C 尝试 + 硬件状态异常（2026-11-22 22:00）

### 用户新指令
- 把 UART7 的 TX/RX 恢复普通 GPIO，当软件 I2C 用：**TX(PE8)=SCL、RX(PE7)=SDA**（接线不变）。

### 手册关键结论（`Source/八路巡线红外传感器/0.8路巡线模块的使用方法/8路巡线模块的使用方法.pdf`）
- 模块支持 3 种协议：直接 IO 电平（仅数字）、USART（模拟+数字）、**I2C（仅数字）**。
- **I2C 设备地址 = 0x12（7-bit）**；**寄存器 0x30（R）** = 8 路状态字节（bit0=x1..bit7=x8，0=亮灯/黑线）。
- 读法：START → 写 0x24(0x12<<1) → 写 0x30 → ReSTART → 读 0x25(0x12<<1|1) 1 字节 → STOP。
- 上电后需等 20s 探头稳定；未校准红灯闪，需 KEY1 校准（黑线 3s→按键→白线 3s→按键）。

### 已实现（代码）
- `Bsp/soft_i2c.c/h`：移植原厂 `sccb.c` 位拆 I2C（start/stop/ack/read/write/scan/probe），SCL=PE8、SDA=PE7 开漏。
- main.c 注释 MX_UART7_Init、调 si2c_init；prot_8irtraking.c init 改 I2C 扫描；chassis 调 prot_8ir_i2c_read() 读 0x12/0x30 填 s_data.digital + compute_position。
- 编译 0 Error。

### 实验结果（异常）
- 软 I2C 版烧录后 **COM134 完全 0 字节**（连 [SYS] 都没有）——固件整体没起来。
- **回滚到 UART 稳定版后仍然 0 字节** → 判断不是软件版本问题，而是**硬件状态变化**：用户接回寻线模块后 MCU/调试器链路异常。
- 现象对比：接 USB-TTL（下午 C33）时系统正常；接寻线模块（带自身供电）后 COM134 停工。高度怀疑模块供电/信号线把 U7 或板子某处拉住，或 DAP 的 2M UART 与模块电气冲突。

### 下一步（需用户现场配合，按顺序）
1. **断开寻线模块所有线**（只留 DAP+24V+USB），烧录后看 COM134 是否恢复 [SYS] → 确认模块是元凶。
2. 若恢复：单独给模块供电，只接 SDA(PE7)/SCL(PE8)，确认 3.3V 还是 5V 电平（I2C 需外部上拉，模块可能没有 → 需在 MCU 端加 4.7k 上拉到 3.3V）。
3. 用逻辑分析仪/示波器看 PE8/PE7 是否有波形（I2C 扫描时）。
4. 若模块确实是 I2C 从机且电平匹配，重烧软 I2C 版（代码已写好，回滚前版本可从本日志描述重建）。

### 教训
- 硬件接线变更后先验证"最小系统能跑"（[SYS] 输出），再叠加外设——这次接模块后整个 MCU 停工，如果不做对照实验会误判为软件 bug。
